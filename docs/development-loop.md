# AI 에이전트 협업 개발 루프

이 문서는 두 명의 팀원과 각자의 AI 에이전트가 사용하는 초기 운영 기준입니다. 실제 운영에서 발견한 문제는 Issue로 제안하고 합의 후 갱신합니다.

전체 개발 기간은 10일입니다. 주간 단위 운영 대신 매일 짧게 진행 상황과 검토 병목을 확인하고, 4~5일차에 중간 점검을 진행합니다. 마지막 1~2일에는 통합 플레이, 오류 수정과 최종 검증을 우선하도록 범위를 조정합니다. 일차는 팀이 합의한 개발 시작일을 기준으로 합니다.

- [공유 작업 보드](https://github.com/orgs/jj-game-studio/projects/1)
- [전체 작업과 검토 기록](https://github.com/jj-game-studio/Project-Nomad/issues)

## 공유 기록

- [게임 기획서](game-design.md): 게임 방향과 규칙의 기준입니다. 미정 사항은 관련 Issue에서 결정한 뒤 기획서에 반영합니다.
- GitHub Issue: 목표, 완료 조건, 작업 범위, 담당자, 플레이 검토와 결정 이력의 기준입니다.
- GitHub Projects: Issue의 진행 상태를 함께 확인하는 보드입니다.
- Pull Request(PR): 코드 변경, 기술 검토, 수정 이력을 관리합니다. 관련 Issue를 연결합니다.
- 빌드 또는 테스트 장면: 사람이 실제 동작과 재미를 확인하는 결과물입니다. 실행 방법과 커밋을 기록합니다.
- 개인 에이전트 채팅에서 결정한 내용도 팀에 필요한 사항은 Issue 또는 PR에 요약합니다.

## 역할과 할당

두 팀원의 에이전트가 작업 실행과 기술 조율을 담당하며 GitHub 기록으로 협업합니다. 각 작업에는 사람 담당 계정과 실행 에이전트를 기록하고, 일반 PR의 검토 담당자는 해당 작업의 사람 담당자로 지정하고, 팀원 전원 합의가 필요한 사안은 모든 팀원을 지정합니다. PR 작성자 본인의 GitHub Reviewers 지정 제한과 승인 기록 방법은 루트 AGENTS.md를 따릅니다. 상세 행동 규칙은 루트 AGENTS.md를 따릅니다.

처음에는 사람이 작업을 지정합니다. 이후에는 사람이 승인한 '할당 가능' 목록에서만 에이전트가 다음 작업을 선택할 수 있습니다. 착수 전에 최신 상태와 댓글을 읽고 담당자를 확인해 중복 작업을 피합니다. 수정 전에 Issue에 에이전트 식별 정보, 브랜치와 예정 수정 영역을 공개합니다. 같은 작업은 한 에이전트만 진행하고, 중복 영역은 에이전트끼리 진행 순서와 범위를 조율합니다. 합의가 안 되거나 사람 판단이 필요하면 담당자에게 요청합니다.

작업 카드는 다음 내용을 포함합니다.

- 목표와 사용자에게 보이는 결과
- 확인 가능한 완료 조건
- 수정 범위와 제외 범위
- 에이전트가 자율 결정할 수 있는 사항과 사람의 판단이 필요한 사항
- 선행 작업, 사람 담당자, 검토자
- 실행 및 검증 방법

한 작업은 독립적으로 검토할 수 있는 크기로 나눕니다. 공용 코드, 장면, 프리팹 등의 수정 범위가 겹치면 순서를 정하거나 작업을 분리합니다.

## 보드 상태

라벨은 작업의 성격을 분류하고, 진행 상태는 보드의 Status로 관리합니다. 기본 라벨은 `기획`, `기능`, `아트`, `오디오`, `버그`, `검증`, `문서`, `운영`, `환경`, `개선`입니다. 사람의 결정이 필요하거나 진행이 막힌 경우에는 각각 `판단 필요`, `진행 막힘`을 추가하고 이유를 댓글에 기록합니다.

| 상태 | 진입 기준 / 다음 행동 |
| --- | --- |
| 후보 | 아이디어 또는 미정 사항. 바로 구현하지 않습니다. |
| 할당 가능 | 목표, 완료 조건, 범위, 의존성과 담당자가 정해졌고 사람 판단 대상에는 검토자가 지정되었습니다. |
| 작업 중 | 에이전트가 착수하고 구현·검증합니다. |
| 검토 대기 | 검증과 제출 자료를 갖췄으며 검토 대상 커밋이 고정되었습니다. |
| 수정 중 | 필수 수정 의견을 반영하고 다시 검증합니다. |
| 완료 | 병합 조건을 충족하고 필요한 병합과 통합 확인이 끝났습니다. 사람 판단 대상은 사람이 검토하고 직접 병합했습니다. |

막힌 작업은 현재 상태를 유지하고 Issue 댓글에 원인, 필요한 결정, 진행 가능한 부분을 기록합니다. 해결 전에는 할당 가능으로 되돌려 다른 에이전트가 중복 착수하게 하지 않습니다.

초기 운영에서는 사람별 작업 중 1개와 검토 대기 1개를 권장 상한으로 삼습니다. 검토 대기가 쌓이면 새 작업보다 검토와 제출 품질 개선을 우선합니다.

## 구현과 제출

1. 에이전트는 Issue, 최신 댓글, 저장소 지침을 읽습니다.
2. Issue에 착수를 공개하고 작업별 브랜치에서 필요한 범위만 수정합니다. 병렬 작업은 checkout 또는 worktree를 분리합니다. 최초 커밋을 푸시한 직후 Draft PR을 생성하고, 생성 전에는 추가 커밋을 하지 않습니다.
3. 완료 조건에 맞춰 실행·검증하고 발견한 문제를 수정합니다. 실행하지 못한 검사는 통과로 보고하지 않습니다.
4. Draft PR과 Issue를 연결하고 제출 준비가 끝나면 Draft를 해제합니다. 검토할 커밋, 변경 요약, 검증 결과, 실행 방법, 알려진 문제, 사람의 판단이 필요한 사항을 남깁니다.
5. 보드를 검토 대기로 옮깁니다. 검토 도중 변경이 필요하면 수정 사실과 새 커밋을 알려 재검토를 요청합니다.

검토 대기 중에는 승인되지 않은 결과에 의존하지 않는 별도 작업만 진행합니다. 다음 작업이 없으면 대기하거나 독립적인 조사 결과를 제안합니다.

## 사람 검토와 수정

에이전트는 컴파일, 요구사항 누락, 오류와 회귀를 검증합니다. 사람은 조작감, 재미, 연출, 아트 일관성과 최종 수용 여부를 판단합니다. 자동 검사 통과만으로 재미가 검증되었다고 간주하지 않습니다.

- 기술 검토는 PR에, 플레이 검토와 제품 결정은 Issue에 남기고 서로 링크합니다.
- 의견에는 관찰한 현상, 수정 요청, 확인 조건을 적습니다.
- 반드시 고칠 항목은 `[필수]`, 후속 아이디어는 `[후속]`, 결정이 필요한 질문은 `[질문]`으로 구분합니다.
- 후속 아이디어는 별도 Issue로 분리하고 현재 작업의 완료 범위를 계속 늘리지 않습니다.
- 에이전트는 필수 의견별 변경 내용과 검증 결과를 답하고 검토 대기로 돌립니다.
- 사람 판단이 필요 없는 일반 PR은 완료 조건과 검증을 충족하고 필수 의견·충돌·미해결 의존성이 없으면 에이전트가 자율 병합할 수 있습니다. 저장소 보호 규칙은 준수합니다.
- 재미, 조작감, 게임 규칙, 연출·아트 방향, 합의 범위나 큰 공용 구조 변경 등 사람 판단 대상은 사람이 검토하고 직접 병합합니다. 에이전트 검토로 이를 대체하지 않습니다.

해당 PR의 병합 조건에 따라 병합 및 통합 확인을 마치고 Issue를 닫으며 보드를 완료로 옮깁니다. PR 병합만으로 플레이 검토가 생략되지 않도록, 플레이 승인이 남았다면 `Closes #번호` 같은 자동 종료 문구를 사용하지 않습니다.

## 검토 리듬과 개선

수시로 개별 검토를 하되 하루 두 번 검토 시간을 확보하는 방식으로 시작합니다. 구체적인 시간은 팀이 정합니다. 함께 플레이하는 시간에는 개별 기능뿐 아니라 기능을 합친 게임 경험을 확인합니다.

첫날부터 검토 요청 시점, 검토 결과 시점, 재작업 이유를 기록하고 매일 짧게 확인합니다. 4~5일차 중간 점검에서는 요구사항 오해가 많으면 작업 명세를, 실행 오류가 많으면 자동 검증을, 재미 수정이 많으면 초기 플레이 확인을 개선합니다. 10일 내 완료를 위해 개선은 남은 개발에 바로 도움이 되는 작은 변경을 우선합니다.

## 에이전트 연결과 자동 실행

사람은 GitHub 웹 화면을 사용하고 에이전트는 인증된 GitHub MCP, CLI 또는 API로 Issue·댓글·PR·보드에 접근합니다. 저장소와 Projects의 접근 권한은 각각 확인해야 합니다.

보드 생성만으로 에이전트가 자동 실행되지는 않습니다. 초기에는 사람이 'Issue #번호 진행' 또는 '검토 의견 반영'을 요청합니다. 자동 실행은 중복 착수 방지, 승인 경계와 실패 보고 방식을 확인한 뒤 별도 작업으로 도입합니다.
